# تحلیل چالش ۲: Trace Tracking & Multi-layer Analysis

## ۱. بررسی و تحلیل داده‌های موجود

### الف) تحلیل لاگ‌ها

| فیلد | ComplaintReceived | ComplaintStored | TrackingRequested | TrackingFailed |
|------|---|---|---|---|
| trace_id | TRC-1001 | TRC-1001 | TRC-1001 | TRC-1001 |
| request_id | RQ-2001 | RQ-2001 | RQ-2002 | RQ-2002 |
| complaint_id | CMP-9001 | CMP-9001 | CMP-9001 | CMP-9001 |
| response_time_ms | 1200 | 400 | 300 | 200 |

### ب) تناقضات کشف‌شده

**مشکل ۱ — ناسازگاری response_time در متریک vs لاگ:**

- لاگ: `ComplaintReceived = 1200ms` و `ComplaintStored = 400ms` → میانگین واقعی = **800ms** ✅ (با متریک همخوانی دارد)
- لاگ: `TrackingRequested = 300ms` و `TrackingFailed = 200ms` → میانگین واقعی = **250ms** ✅

**مشکل ۲ — خطای NOT_FOUND در TrackingFailed:**

فاصله زمانی بین `ComplaintStored` (12:10:09) و `TrackingRequested` (12:10:17) فقط **8 ثانیه** است. احتمال قوی: سرویس `request_tracking` هنگام جستجو، شکایت هنوز در DB commit نشده یا ایندکس نشده بود → **Race Condition / Eventual Consistency Issue**

**مشکل ۳ — نمودار drawio ناقص است:**
- هیچ نودی برای حالت خطا (Error/Retry) وجود ندارد
- وابستگی بین `complaint_register` و `request_tracking` نشان داده نشده
- نود پایانی (End) غایب است
- حالت‌های موفق و ناموفق تفکیک نشده‌اند

## ۲. جدول تحلیل اختلال سیستمی

| # | نوع اختلال | سرویس آسیب‌دیده | علت ریشه‌ای | شواهد |
|---|---|---|---|---|
| 1 | Race Condition | request_tracking | ذخیره‌سازی async در complaint_register باعث می‌شود tracking قبل از commit کامل اجرا شود | فاصله 8 ثانیه‌ای + خطای NOT_FOUND |
| 2 | Missing Retry Logic | request_tracking | هیچ مکانیزم retry/fallback در لاگ دیده نمی‌شود | بلافاصله بعد از TrackingRequested → TrackingFailed |
| 3 | Error Rate 100% | request_tracking | هر درخواست tracking شکست می‌خورد | متریک: error_count=1, total_requests=1 |
| 4 | Missing End State | نمودار | فرآیند end-to-end بدون وضعیت پایانی تعریف شده | drawio فاقد End node و Error path |

## ۵. نتیجه‌گیری: ریشه اختلال سیستمی

```
علت اصلی: Race Condition بین complaint_register و request_tracking

جریان مشکل‌ساز:
  ComplaintStored (12:10:09) 
       ↓ فقط 8 ثانیه فاصله
  TrackingRequested (12:10:17) ← DB هنوز fully consistent نیست
       ↓
  NOT_FOUND → TrackingFailed (12:10:18)

راه‌حل پیشنهادی:
  ۱. افزودن تاخیر یا polling با retry (حداقل 3 بار با back-off)
  ۲. استفاده از event-driven pattern: complaint_register پس از commit 
     یک event publish کند و tracking subscriber آن باشد
  ۳. لاگ کردن RetryAttempt برای observability کامل
```
