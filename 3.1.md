## تحلیل چالش ۱: نقص داده‌ها در لاگ و متریک

### ۱. شناسایی نقص‌های داده‌ای

**لاگ JSON — نقص‌های شناسایی‌شده:**

| ردیف | فیلد ناقص | رویداد آسیب‌دیده | توضیح |
|------|-----------|-----------------|-------|
| ۱ | `trace_id` | همه رویدادها | هیچ رویدادی شناسه رهگیری ندارد — ردیابی جریان میان‌سرویس غیرممکن است |
| ۲ | `duration_ms` | همه رویدادها | مدت زمان پاسخ‌دهی هیچ رویدادی ثبت نشده |
| ۳ | `request_id` | همه رویدادها | شناسه یکتای درخواست غایب است |
| ۴ | `session_id` | همه رویدادها | امکان ردیابی جلسه کاربر وجود ندارد |
| ۵ | `error_message` | `PaymentProcessingFailed` | کد خطا هست ولی پیام توصیفی ندارد |
| ۶ | `retry_count` | `PaymentProcessingFailed` | مشخص نیست آیا retry انجام شده یا نه |
| ۷ | `payment_method` | `PaymentRequestReceived` | روش پرداخت ثبت نشده |
| ۸ | `correlation` بین سرویس‌ها | کل لاگ | رویداد پرداخت قبل از استعلام خلافی است — ترتیب منطقی معکوس |

**متریک Markdown — نقص‌های شناسایی‌شده:**

| ردیف | نقص | توضیح |
|------|-----|-------|
| ۱ | `error_rate` نداریم | باید به‌صورت درصد محاسبه و نمایش داده شود |
| ۲ | `avg_response_time` نداریم | بدون این فیلد، SLA قابل ارزیابی نیست |
| ۳ | `success_count` نداریم | تعداد موفق محاسبه‌پذیر نیست بدون محاسبه |
| ۴ | `timestamp` نداریم | متریک به بازه زمانی خاصی منتسب نیست |
| ۵ | `p95_latency` نداریم | توزیع تأخیر نامشخص است |

**نمودار Draw.io — نقص‌های شناسایی‌شده:**

| ردیف | نقص |
|------|-----|
| ۱ | گره پایانی (End) وجود ندارد |
| ۲ | مرحله «پرداخت ناموفق / retry» وجود ندارد |
| ۳ | مرحله «نتیجه استعلام» وجود ندارد |
| ۴ | فلوی شرطی (decision node) برای موفق/ناموفق بودن پرداخت نیست |
| ۵ | `trace_id` روی لینک‌های فلو نمایش داده نشده |

### ۲. نسخه اصلاح‌شده لاگ JSON

**original_code:**
```json
{
  "timestamp": "2024-06-15T10:23:12Z",
  "service": "payment",
  "level": "INFO",
  "event": "PaymentRequestReceived",
  "user_id": "U12345",
  "amount": 120000
}
```

**expected_code:**
```json
{
  "timestamp": "2024-06-15T10:23:12Z",
  "service": "payment",
  "level": "INFO",
  "event": "PaymentRequestReceived",
  "trace_id": "TRC-20240615-001",
  "request_id": "REQ-PAY-0012",
  "session_id": "SES-U12345-0001",
  "user_id": "U12345",

  "payment_method": "online_banking",

```

```
| payment           | 2024-06-15T10:23Z   | 1             | 0             | 1           | 100.00%    | 1000            | 1000           |
```

### ۴. تحلیل وابستگی و کشف گلوگاه

**زنجیره وابستگی منطقی:**

```
کاربر → استعلام خلافی → (نتیجه استعلام) → پرداخت عوارض
```

- سرویس `payment` به نتیجه موفق `violation_inquiry` **وابسته است**؛ اگر استعلام انجام نشده باشد، پرداخت نباید آغاز شود.
- در لاگ اصلی، پرداخت **قبل** از استعلام شروع شده — نشانه‌ای از **عدم وجود بررسی پیش‌شرط** در سرویس پرداخت.

**گلوگاه اصلی: `BANK_CONN_TIMEOUT`**

سرویس پرداخت با خطای timeout درگاه بانکی مواجه شده، اما:
- هیچ مکانیزم retry ثبت نشده
- هیچ fallback یا circuit-breaker فعال نشده
- کاربر از نتیجه نهایی بی‌خبر مانده

### ۶. خلاصه یافته‌های چالش ۱

| دسته | مشکل | شدت |
|------|------|-----|
| لاگ | غیاب `trace_id` در همه رویدادها | بحرانی |
| لاگ | ترتیب زمانی معکوس (payment قبل از inquiry) | بحرانی |
| لاگ | نبود `duration_ms` | متوسط |
| لاگ | نبود `error_message` توصیفی در خطا | متوسط |
| متریک | نبود `error_rate`، `avg_response_ms`، `timestamp` | بحرانی |
| نمودار | نبود decision node، مسیر خطا، و End | متوسط |
| سیستمی | گلوگاه: `BANK_CONN_TIMEOUT` بدون retry | بحرانی |
